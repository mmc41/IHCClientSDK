# ADR-003: The generated SOAP layer stays public — XmlSerializer binds only public types

## Status

Decided — 2026-08-17. Settles the visibility question `ARCHITECTURE.md` invariant 9 records as a gap, and the
neutral implication ADR-002 carried forward ("generated SOAP types remain technically `public` though out of
contract"). Does not supersede ADR-002; it refines one of its recorded consequences.

Revisit triggers: (a) the SDK stops using `XmlSerializer` for the controller wire path; (b) a .NET release
lets `XmlSerializer` bind non-public types; (c) before `ihcclient` is published as a NuGet package, since a
released package converts a source-level detail into a distributed contract; (d) a vendor WSDL revision that
changes the generated surface.

## Decision at a glance

The generated `Ihc.Soap.*` layer is emitted `public` deliberately, not by omission. The alternative —
`dotnet-svcutil --internal` — is closed by the serializer: `XmlSerializer` processes only public types, and
the SDK hands it the generated message wrappers on every request. The anti-corruption boundary is therefore
kept where it already is — in signatures and dependency direction, enforced by architecture tests — rather
than in compiler accessibility.

## Context

**Current state** (2026-08-17; version 0.8.1, `net10.0`; source-referenced, no NuGet package per `README.md:42`):

- `ihcclient/generatedsrc/` holds 15 files generated by `dotnet-svcutil` from checked-in WSDLs. The generator
  is invoked with no visibility flag (`generate.sh:14`), so `public` is the tool's default output.
- Each API service holds a private nested `SoapImpl` implementing the generated contract interface
  (`authenticationService.cs:57`); the public interface exposes only SDK models — the anti-corruption layer
  described in `ARCHITECTURE.md:270`.
- The transport is the SDK's own: `ServiceBaseImpl.soapPost` serializes `RequestEnvelope<REQ>` where `REQ` is
  always a generated message wrapper (`serviceBase.cs:109`), and hands the generated type to `XmlSerializer`
  three ways — as generic argument, as `extraTypes`, and as namespace-override key (`serialize.cs:46,66,81`).
- The generated `*Client`/`*Channel` WCF proxies are compiled but referenced by no handwritten code
  (`ARCHITECTURE.md:48`). Their suppression is a separate surface question, out of scope here.
- Outside `ihcclient`, only two test assemblies reference `Ihc.Soap.*`: `safe_unit_tests` (a friend assembly)
  and `safe_architecture_tests`, which is deliberately *not* a friend so that its layer anchors are public
  types (`IhcClientArchitectureTests.cs:39`).

**Decision forces**: invariant 9 (`ARCHITECTURE.md:88`) admits the visible surface as a gap — vendor WSDL
churn would surface as this SDK's own breaking changes. Both candidate resolutions were on the table and
neither had been tested, leaving the surface neither hidden nor deliberately accepted.

**Reversibility**: two-way door. No package is published and no SemVer commitment exists, so visibility can
be revisited without breaking a distributed contract. The cost of reversing is set by the serialization
mechanism, which this decision does not change. Publishing a package would harden it (trigger c).

## Evaluation Criteria

Priority order (highest first) — the first is decisive: an option that breaks the wire path is unavailable
whatever else it scores.

1. **Wire-path correctness** — every SOAP request and response still serializes at runtime.
2. **Vendor-churn isolation** — how much generated, WSDL-shaped detail is hidden from consumers.
3. **Boundary enforceability** — whether "do not use this layer" is mechanically checked rather than asserted.
4. **Test-suite viability** — white-box serialization tests, SOAP-contract fakes, and typeof-anchored layer rules keep working.
5. **Adoption and maintenance cost** — effort to adopt and to keep working across regenerations.

## Options

### 1. Keep the layer public; enforce the boundary in signatures and dependency direction (chosen)

The generator keeps its current flags. The anti-corruption layer stays the mechanism: generated types are
reachable but appear in no public signature, and no tier above the private `SoapImpl` adapters may depend on
them. Architecture tests fail the build on violation, and their layer anchors resolve through a public
generated type, so a rename breaks the compile rather than silently matching nothing.

| Criteria | Score | Rationale |
| --- | --- | --- |
| Wire-path correctness | 5/5 | The serializer's public-type requirement is satisfied by construction; this is the configuration in service today |
| Vendor-churn isolation | 2/5 | Positional WSDL artifacts such as `inputMessageName7` stay visible; isolation rests on convention plus documentation, not on the compiler |
| Boundary enforceability | 4/5 | Dependency rules and a recursive public-signature scan already fail the build, but they bind first-party code only |
| Test-suite viability | 5/5 | Serialization tests, FakeItEasy fakes over generated contracts, and the public typeof anchors all keep working unchanged |
| Adoption and maintenance cost | 5/5 | No code, generator, or fixture change |
| | **Total: 21/25** | **Trade-offs**: accepts a permanently visible vendor-shaped surface; buys correctness, testability and zero cost |

### 2. Emit the generated layer internal (`dotnet-svcutil --internal`)

The generator flag exists and applies cleanly: roughly four fifths of the generated type declarations become
internal, and the solution compiles. It fails at runtime. `XmlSerializer` rejects the internalized message
wrappers with *"is inaccessible due to its protection level. Only public types can be processed"*, and because
`RequestEnvelope<T>` closes over those types, even constructing a serializer fails. Friend assemblies do not
help — the accessibility check precedes serializer codegen. The `WS*` data types stay public regardless, for
the same reason.

| Criteria | Score | Rationale |
| --- | --- | --- |
| Wire-path correctness | 1/5 | Every SOAP request fails at runtime; observed on the controller-free suites, which fail wholesale on the serialization paths |
| Vendor-churn isolation | 4/5 | Hides contracts, wrappers and proxies, but the `WS*` data types must remain public, so the vendor vocabulary stays partly visible |
| Boundary enforceability | 5/5 | The compiler enforces it; no rule or reviewer needed |
| Test-suite viability | 1/5 | The layer-rule fixture loses its public anchor and would need friend access, contradicting its own design; faking an internal contract additionally requires exposing internals to the proxy generator |
| Adoption and maintenance cost | 3/5 | One generator flag, but the architecture fixture's anchors and seeded positive control must be re-based |
| | **Total: 14/25** | **Trade-offs**: buys compiler-enforced encapsulation at the cost of the wire path itself |

### 3. Replace the serializer, then internalize

Hand-write or source-generate the XML layer so no reflection-based serializer constrains visibility, then emit
the generated types internal. This is the only route that makes full internalization reachable. It re-implements
the serialization of a reverse-engineered vendor dialect across 15 services, where the current suites pin
behaviour that a rewrite must reproduce exactly.

| Criteria | Score | Rationale |
| --- | --- | --- |
| Wire-path correctness | 3/5 | Achievable, but re-implementing a reverse-engineered dialect risks regressions the vendor will not document |
| Vendor-churn isolation | 5/5 | Full internalization becomes possible, including the data types |
| Boundary enforceability | 5/5 | The compiler enforces it |
| Test-suite viability | 2/5 | Inherits option 2's anchor and faking problems, and the serialization tests must be rewritten against the new layer |
| Adoption and maintenance cost | 1/5 | Replaces the transport layer of the whole SOAP surface and adds permanent bespoke code for a sole maintainer |
| | **Total: 16/25** | **Trade-offs**: the only path to real encapsulation, at the price of owning the wire format by hand |

## Decision

Adopt option 1: the generated `Ihc.Soap.*` layer is public by intent.

- The decisive criterion settles it. The SDK's own transport hands generated message wrappers to
  `XmlSerializer` on every call, and that serializer binds public types only. Option 2 was tried end to end
  rather than reasoned about: it builds warning-free and then fails at runtime on the first serialization.
- Encapsulation is bought where it is affordable. The generated vocabulary is kept out of every public
  signature by the private `SoapImpl` adapters, and out of every tier above them by dependency rules. That is
  a narrower guarantee than inaccessibility, and it is the guarantee this SDK offers.
- Option 3 is the only route to the stronger guarantee and remains available. It is declined on cost: it
  trades a documented, mechanically checked convention for permanent ownership of a reverse-engineered wire
  format, at sole-maintainer capacity.
- The exposure this accepts is bounded today by distribution: the SDK is referenced as source, with no
  package and no SemVer commitment, so a later reversal breaks no published contract.

Confidence: high — the deciding constraint is platform behaviour, observed directly rather than inferred, and
it eliminates the alternative independently of preference. Top unresolved uncertainty: whether any external
consumer has bound to `Ihc.Soap.*`; with no package published this is unobservable, and publishing one is the
event that would make it matter.

## Implications

### Positive

- The wire path keeps a single serialization mechanism, with no bespoke XML code to maintain across vendor
  WSDL revisions.
- White-box serialization tests and fakes over generated contracts stay expressible, so the SOAP layer remains
  testable without a controller.
- Layer rules keep resolving their forbidden namespace through a public generated type, so renaming it breaks
  the compile instead of leaving a rule that matches nothing.

### Negative

- Vendor-shaped identifiers such as `inputMessageName7` are permanently visible to anyone referencing the SDK,
  and a WSDL revision changes types that are nominally public.
- The boundary constrains first-party code only. A third-party consumer can bind to the generated layer, and
  nothing mechanical prevents it.
- Should a package ever be published, this surface ships with it, and the reversal cost rises from a generator
  flag to a consumer-visible break.

### Neutral

- The `*Client`/`*Channel` proxies remain compiled and unreferenced; whether to keep emitting them is a
  separate question this decision does not settle.
- The `InternalsVisibleTo` friend list is unaffected, and `safe_architecture_tests` stays off it by design.
- Invariant 9's visibility note describes an accepted property of the SDK rather than an open question.

## Confirmation

- Architecture fitness tests: the application tier and the GUI must not depend on `Ihc.Soap.*`, and a
  recursive public-signature scan asserts no `IIHCApiService` contract or implementation exposes a generated
  type. The scan carries a seeded positive control so it cannot pass vacuously.
- A repo-wide compile-time ban on the `Ihc.Soap` namespace. A project that owns or white-boxes the layer
  opts out through a property in its own file, so every exception is greppable.
- The SDK's public surface is pinned as a checked-in baseline, which deliberately excludes this layer.
- The generator scripts carry no visibility flag; a change to that flag set is a review trigger.

## Consultation

Ruled by the repository owner and sole maintainer on 2026-08-17, on evidence from an executed spike rather
than from analysis alone: the internal-emission alternative was generated, built and run against the
controller-free suites before being reverted. No external stakeholders were consulted — the SDK is unofficial
and single-maintainer.
